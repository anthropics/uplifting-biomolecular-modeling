# RF3_HOIST — what is hoisted, from which code path, and why each tensor cannot depend on the step index, the noise level t̂, or x_t
Source: RosettaCommons/foundry @ 4010e3e + the kit's five patched files (`../patched/rf3/`, README.md beside this directory). Flag `RF3_HOIST` (default 0 = the un-hoisted code path).

## 0. The call structure that makes hoisting legal
`RF3WithConfidence.forward` (rf3/model/RF3.py L476-488; RF3.forward L201 likewise) calls, ONCE per (design, seed) fold and AFTER the trunk has finished,
`inference_sampler.sample_diffusion_like_af3(f=input["f"], S_inputs_I=recycling_outputs["S_inputs_I"], S_trunk_I=recycling_outputs["S_I"], Z_trunk_II=recycling_outputs["Z_II"], diffusion_module=self.diffusion_module, diffusion_batch_size, coord_atom_lvl_to_be_noised)`.
Inside the sampler (rf3/diffusion_samplers/inference_sampler.py, stock `for c_t_minus_1, c_t in zip(noise_schedule, noise_schedule[1:])` loop, and identically the CUDA-graph roll-out's `_step_body`), the ONLY per-step call into the network is
`diffusion_module(X_noisy_L=X_noisy_L, t=t_hat.tile(D), f=f, S_inputs_I=S_inputs_I, S_trunk_I=S_trunk_I, Z_trunk_II=Z_trunk_II)`.
The Python objects `f` (feature dict), `S_inputs_I`, `S_trunk_I`, `Z_trunk_II` passed to every one of the 199 calls are the SAME objects (same `id`, never reassigned inside the loop), and no code in the roll-out writes into them: `f` is only read (`f[...]` loads; the one in-place op on an `f` entry, `f["ref_atom_name_chars"] = f["ref_atom_name_chars"].reshape(L, -1)` in the encoder, is an idempotent reshape of a step-independent feature), and the three trunk tensors are only consumed through `.float()` / `torch.cat` / `nn.Linear` / `LayerNorm`, all out-of-place. The model is in `eval()` (engine `initialize()` -> `trainer.state["model"].eval()`), under `torch.no_grad()`, autocast bf16 — the same for every step. There is no dropout / stochastic depth / RNG use anywhere in `DiffusionModule.forward` (grep `dropout|Dropout|torch.rand|bernoulli` over rf3/model/RF3_structure.py, rf3/model/layers/af3_diffusion_transformer.py, rf3/model/layers/layer_utils.py: no hits; the only RNG in the roll-out is the sampler's own noise/augmentation draws, which act on X only).
Therefore any sub-expression of `DiffusionModule.forward` whose free variables are a subset of {`f`, `S_inputs_I`, `S_trunk_I`, `Z_trunk_II`, module parameters/buffers, Python constants} evaluates the same kernels on the same input bits at every step, and (CUDA kernels used here being run-to-run deterministic for identical inputs and shapes on one device: LayerNorm, GEMM with fixed cuBLAS heuristics for a fixed shape, elementwise, cat, gather — no atomics-based reductions in these sub-graphs; `index_reduce`/scatter_mean, the one atomics op in the step, is NOT hoisted) produces the same bits. The X-dependence enters `DiffusionModule.forward` only through `X_noisy_L` and `t`; below, every hoisted tensor is listed with its defining expression and its free variables.

The cache is keyed by `(id(module instance), name)`, created empty at the start of every `sample_diffusion_like_af3` call and dropped (after a device sync) in a `finally:` at its end (graph_flags.hoist_begin/hoist_end), so a cached tensor can never leak across folds/designs/seeds (different `f`/trunk outputs) or across the two sampler instances; outside a roll-out (`HOIST_CACHE is None`) every module takes the stock branch (this covers the training-branch single denoising step in RF3.forward, the mini-rollout sampler being a separate `sample_diffusion_like_af3` call with its own cache, and CPU inputs).

## 2. Why "same bits", not just "same maths"
Each hoisted entry is produced by calling the **stock sub-module objects** on the **same tensor objects** the stock step would use, in the same dtype context (the roll-out's autocast region), so the first-step computation IS the stock computation of that step; reuse at later steps returns that tensor instead of re-launching identical kernels on identical inputs. Kernel-level determinism of these sub-graphs for identical inputs (no atomics; fixed shapes -> fixed cuBLAS/cuBLASLt algorithm choice within a process) is what lets the cache-hit path return exactly the bits the stock step would recompute: `X_denoised` with the hoist (cache-miss path and cache-hit path alike) equals stock's at the same (X_noisy, t) bit for bit; the step's one atomics op (`scatter_mean`) lies outside every hoisted sub-graph.
Two things the cache deliberately does NOT assume: (i) that `f` is unchanged across folds (cache lifetime = one roll-out); (ii) that CUDA-graph capture sees stable addresses — under RF3_CUDAGRAPH=1 the roll-out's warm-up steps (eager) fill the cache before capture, the captured graph then reads the cached tensors as constants (they stay allocated until `hoist_end`, which synchronizes before dropping them, after the last replay).

## 3. What would break the invariance (and is therefore guarded)
- A future sampler that modifies `f` or the trunk tensors between steps (e.g. self-conditioning) would break it — the hoist is legal only for the call structure of §0; the cache is per roll-out so cross-fold staleness is impossible by construction.
- Training mode (dropout-free here, but `embed_atom_feats` has a `self.training` branch with a different op order) -> `_forward_hoisted` is only entered when `not self.training`.
- `SamplePartialDiffusion` (partial diffusion) shares the dispatcher and therefore the same cache lifecycle; its per-step call has the same signature (same invariants).
